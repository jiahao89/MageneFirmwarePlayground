## Problem Statement

产品经理目前可以直接使用 Claude Code，但没有一个简单、可恢复的入口来处理原始需求。需求识别、需求登记、Agent 提问、PM 回答、PRD 产出和完成状态分散在聊天与本地文件中。

对于不熟悉 Git 和命令行的 PM，最关键的困难是：不知道应该把 Claude Code 启动在哪个目录，也无法确认 Agent 是否拿到了 MFP 的项目规则、知识库和当前需求上下文。

本任务只解决一条最小闭环，不解决团队协作和多 Agent 适配：

```text
手动输入需求 → Web 识别 → PM 确认 → 打开 MFP 目录并启动 Claude Code
→ Claude Code 写回问题/PRD → Web 展示 → PM 完成确认
```

## Solution

构建一个本地运行的 MFP MVP，由三部分组成：

1. **Web 操作台**：手动输入原始需求，查看识别结果、需求状态、澄清问题和 Markdown PRD。
2. **本地桥接层**：负责本地文件读写、调用 Claude Code CLI、设置工作目录、打开外部终端、启动/恢复会话和监听工作包变化。
3. **Claude Code 执行环境**：使用 PM 自己安装并登录的 Claude Code；读取 MFP 项目规则、任务卡和 benchmark，完成识别、澄清与 PRD 生成。

MVP 推荐使用 Tauri + React 作为桌面壳和 Web UI。普通浏览器不能可靠地启动本地终端，因此“打开指定目录并自动开启 Claude Code 会话”必须由本地桌面桥接层完成。

Web 端的“识别”不是浏览器直接调用固定 AI API，而是桥接层调用 Claude Code 的非交互模式，要求返回结构化 JSON。正式工作阶段再打开外部终端启动交互会话。MFP 不保存 Claude Code 的 API Key 或登录凭据。

## User Stories

1. As a product manager, I want to paste a customer message into MFP, so that I can start processing a requirement without learning Git or command-line syntax.
2. As a product manager, I want the original text to be saved before AI processing starts, so that a failed recognition never loses the source material.
3. As a product manager, I want to add a short source description, so that I can later understand where the requirement came from.
4. As a product manager, I want MFP to generate a raw-input identifier, so that each incoming request can be found and referenced.
5. As a product manager, I want Claude Code to classify the input as a feature request, bug, consultation, research item, invalid input, or duplicate candidate, so that I know how to handle it.
6. As a product manager, I want Claude Code to rewrite the original text as a functional requirement, so that I can review an actionable version instead of a vague customer statement.
7. As a product manager, I want to see the user, scenario, goal, scope clues, known constraints, and missing information, so that I can judge whether the rewrite is usable.
8. As a product manager, I want to see evidence and uncertainty labels, so that AI judgments are not mistaken for confirmed Magene facts.
9. As a product manager, I want MFP to show possible duplicate or conflicting requirements, so that I can decide whether to archive or create a separate request.
10. As a product manager, I want to explicitly confirm registration, so that AI cannot create a formal requirement without my decision.
11. As a product manager, I want MFP to create a stable formal request identifier and work package after confirmation, so that later Agent runs have a durable context.
12. As a product manager, I want to see the next action and current status in a requirement pool, so that I know whether I need to respond or review an output.
13. As a product manager, I want MFP to check whether Claude Code is installed and the MFP workspace is readable and writable, so that I receive a useful error before a session starts.
14. As a product manager, I want MFP to open Claude Code in the MFP project root, so that the Agent can discover `AGENTS.md`, the knowledge base, skills, and the active work package.
15. As a product manager, I want MFP to automatically start a named Claude Code session with the active task context, so that I do not need to manually copy a prompt.
16. As a product manager, I want the active Claude Code session identifier to be saved, so that I can continue the same conversation when the workflow pauses.
17. As a product manager, I want Claude Code to write clarification questions into the work package, so that questions are visible in Web even if the terminal is closed.
18. As a product manager, I want to answer clarification questions in Web, so that I can keep formal decisions in one place.
19. As a product manager, I want MFP to update the task context after I answer, so that Claude Code can continue with the latest confirmed constraints.
20. As a product manager, I want MFP to resume the existing Claude Code session when possible, so that the Agent can continue without losing conversation context.
21. As a product manager, I want a new session to be able to continue from the work package when resume fails, so that a closed terminal does not block the request.
22. As a product manager, I want Claude Code to write a Markdown PRD to the agreed output area, so that the PRD remains editable and portable.
23. As a product manager, I want to preview the generated PRD in Web, so that I do not need to search through directories.
24. As a product manager, I want to submit revision comments, so that Claude Code can update the PRD based on explicit feedback.
25. As a product manager, I want to see the new PRD version and a change summary, so that I can verify whether my comments were applied.
26. As a product manager, I want completion to require an explicit Web action, so that an unfinished draft is never treated as final.
27. As a product manager, I want MFP to retain status, questions, answers, logs, session metadata, and outputs after the Web app closes, so that the workflow is recoverable.
28. As a product manager, I want actionable errors for missing CLI, authentication failure, permission failure, timeout, and malformed Agent output, so that I know how to recover.
29. As a product manager, I want the MVP to work on macOS and Windows, so that the team can use the same workflow on different computers.
30. As a developer, I want the MVP to keep Agent-specific logic behind a runtime adapter, so that Codex and Trae can be added later without changing the work package contract.

## Implementation Decisions

### Product and architecture

- Use a local desktop application containing a Web UI and a privileged local bridge. The bridge is the only component allowed to spawn processes or access arbitrary local files.
- Use one runtime adapter in MVP: Claude Code CLI. Do not implement Codex, Trae, remote API providers, team accounts, or cloud synchronization.
- Treat the MFP workspace as the operating context. The bridge must launch Claude Code with the MFP project root as its current working directory.
- Keep the Web UI and Claude Code terminal separate. Web manages workflow state and decisions; Claude Code remains the native Agent work surface.
- Use file-based work packages as the source of truth. A database may be used only as a rebuildable index and must not become the only copy of a requirement.

### Raw input and recognition

- Save raw text and optional source description before invoking Claude Code.
- Invoke Claude Code in non-interactive print mode for recognition. Request JSON output constrained by a schema.
- Recognition output must include category, rewritten requirement, user/scenario, scope clues, known constraints, missing information, evidence references, duplicate candidates, and confidence.
- Recognition must not create a formal request, modify benchmark knowledge, or produce the final PRD.
- Preserve the raw record when recognition fails. The UI must offer retry and show the failure category.

### Registration and work package

- PM actions are the only authority for registration, archiving, and completion.
- Registration creates a stable request identifier and a work package containing the original input, recognition result, task card, questions, answers, evidence, revision comments, run log, session metadata, and generated artifacts.
- The task card is a mutable work contract, not a one-time prompt. It contains current phase, goal, confirmed scope, unresolved questions, allowed context, expected outputs, write-back rules, pause conditions, and prohibited actions.
- The first task phase after registration is “understand and clarify”; the Agent must not jump directly to a final PRD when required information is missing.

### Claude Code launch and session behavior

- Before launch, check CLI availability, version response, MFP root existence, required rules/benchmark entry points, task-card readability, and work-package/output writability.
- Authentication is owned by Claude Code. The bridge must surface the CLI’s authentication error rather than storing or inspecting credentials.
- On macOS, open the configured terminal application; on Windows, prefer Windows Terminal and fall back to PowerShell.
- Start the process with an argument list and an explicit working directory; do not build a shell command by concatenating unsanitized user text.
- Start a new named interactive session with the request identifier and a startup instruction that points Claude Code to `AGENTS.md` and the current task card.
- Save session identifier, CLI version, start time, process state, and last error in session metadata. Never write API keys to metadata or logs.
- When continuing, use the saved session identifier when available. If resume fails, start a new session with the same work package and task card.
- The startup instruction must require the Agent to write formal questions, status updates, logs, and artifacts back to the work package instead of leaving them only in the terminal conversation.

### Web/work-package synchronization

- Prefer filesystem change notifications; use short-interval polling as a fallback.
- The Web UI reads questions, status, run records, and Markdown outputs from the work package.
- The bridge must prevent simultaneous conflicting runs for the same request. The UI should show “running” and disable duplicate start actions.
- If an Agent writes malformed JSON or an invalid status, preserve the raw file, show a diagnostic state, and do not silently infer success.

### MVP state model

The prototype-derived state flow is:

```text
待识别 → 待 PM 确认 → 待启动 → 处理中
处理中 → 待 PM 回答 → 处理中
处理中 → 待审阅 → 修改中 → 待审阅
待审阅 → 完成
待 PM 确认 → 归档
```

Only PM actions may transition a request into formal registration, archive, or completion. Agent writes may move the request into processing, waiting for PM, or waiting for review, subject to validation.

### UI scope

- Original demand page: text input, source description, save, recognition progress, and recognition error.
- Recognition page: classification, rewritten requirement, evidence, missing information, duplicate candidates, and PM actions.
- Requirement pool: identifier, title, status, next action, last updated time, and PRD version.
- Work-package page: task summary, preflight results, “open directory and start Claude Code”, copy task card fallback, and session status.
- Clarification page: Agent questions, PM answers, continue action, and work log summary.
- PRD review page: Markdown preview, revision comments, request-modification action, completion action, and version summary.

### Safety and scope controls

- Keep benchmark and project rules read-only from the MFP bridge’s product workflow. The Agent may read them but must not update them automatically.
- Limit process and file operations to the selected MFP workspace and the configured terminal application.
- Keep command arguments separate from user-authored content; pass long text through controlled task artifacts rather than shell interpolation.
- Do not implement background autonomous runs. Every continue, modify, and complete transition originates from a visible PM action.

## Testing Decisions

### Highest test seam

Use one primary black-box seam: the **local MFP workflow bridge contract**. The test drives the same public operations the Web UI uses—save raw input, recognize, register, preflight, launch, detect questions, answer, resume, generate output, revise, and complete—while replacing the real Claude Code executable with a deterministic fake CLI process.

This seam should assert external behavior, not internal implementation:

- the original input remains available after every failure;
- recognition returns the required structured fields or a visible error;
- registration requires PM confirmation;
- the launched process receives the MFP root as its working directory;
- the startup context points to the rules and task card;
- questions written by the fake Agent appear in Web-facing state;
- PM answers are included when the session resumes;
- PRD output and revision version become visible;
- completion occurs only after PM confirmation.

### Module coverage

- Local bridge process runner and runtime adapter.
- Workspace/work-package persistence and state transitions.
- Recognition result validation and error mapping.
- Session lifecycle: new session, resume, failed resume, and duplicate-run prevention.
- Web-facing read/write service for requirements, questions, revisions, and outputs.
- macOS and Windows terminal launcher as platform smoke tests.

### Test prior art

The current repository contains documentation, skills, scripts, and Agent orchestration but no application runtime or established frontend/backend test suite. There is therefore no existing test harness to extend. The first implementation should establish the bridge contract test as the project’s initial high-level test seam, followed by platform smoke tests on one macOS and one Windows machine.

### Manual acceptance pass

Run one real request end to end with the user’s installed Claude Code after the fake-CLI contract test passes. Confirm that the real process starts in the MFP root, reads the project instructions, writes a clarification question, resumes after a Web answer, and generates a Markdown PRD.

## Out of Scope

- Teambition automatic import or any other source connector.
- Codex, Trae, Gemini, OpenAI API, Anthropic API, or other runtime adapters.
- MFP-owned API keys, centralized model configuration, or credential storage.
- Browser-only deployment without a local bridge.
- Embedded Claude Code terminal or full conversation mirroring inside Web.
- Team accounts, cloud sync, shared workspaces, permissions, comments, and notifications.
- Automatic requirement deduplication, automatic priority decisions, or automatic benchmark updates.
- Automatic publishing to Feishu or Figma.
- Attachments, OCR, image understanding, batch import, and scheduled autonomous runs.
- KPI, efficiency, adoption, or acceptance-rate dashboards.

## Further Notes

- The core implementation question is not “how to send a prompt”, but “how to maintain a durable work contract between Web and Claude Code”. The task card and work package are the contract.
- “Web 端识别” means the PM initiates recognition from Web. The actual AI execution occurs locally through Claude Code print mode.
- “跳转 Claude Code” means opening an external terminal with the MFP root as working directory and starting a named interactive session. It does not mean navigating to a web URL.
- The local bridge should expose a clear adapter boundary so that adding another Agent later is incremental, but no second adapter should be implemented in this MVP.
- Existing Figma screens represent the intended interaction sequence and should be used as visual reference; they are not a substitute for the bridge/work-package contract.
- Before implementation starts, the developer should confirm only the OS terminal preference and packaging approach if those choices affect the launcher. No further product interview is required for the MVP scope above.
