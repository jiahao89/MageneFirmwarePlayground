## 二、本轮修复：双击场景 PATH 解析（发布阻断项）

**缺陷**：GUI 应用经 Finder/Dock 启动时，进程 PATH 为系统最小集（实测本机 `launchctl getenv PATH` 为空，即 `/usr/bin:/bin:/usr/sbin:/sbin`），Homebrew 前缀（`/opt/homebrew/bin`）不在其中。导致：

- Rust 侧 `resolve_node()` 找不到 node → **bridge server 完全无法启动**（实测复现：模拟环境下 app 存活但 bridge 不出现）；
- bridge 侧 `resolveBinaryPath('claude', PATH)` 找不到 claude → preflight `CLI_NOT_FOUND`。

此前验证用 shell `open` 启动 .app，`open` 透传了 shell 的 PATH，掩盖了该缺陷——不是忠实的双击模拟。

**修复**（PATH 扫描失败时按序回退常见安装位置）：

- Rust `resolve_node()` → `/opt/homebrew/bin/node`（Apple Silicon Homebrew）、`/usr/local/bin/node`（Intel Homebrew / 官方 pkg）；显式 `MFP_NODE` 语义不变（优先且不回退）
- TS 适配器 `findBinary()`（仅裸命令名 `claude` 时回退；显式路径不回退，保持测试注入语义）→ `/opt/homebrew/bin/claude`、`/usr/local/bin/claude`、`~/.claude/local/claude`（`claude install` 本地安装位）
- win32 维持 PATH-only（Windows 真机验证另做，符合「不考虑 Windows」边界）

**修复后复验**：最小 PATH + `cwd=/` 双击模拟 → node/脚本/root/adapter 全部正确；打包 bundle + 最小 PATH 的 preflight 8 项全过。

**测试**：npm test **106/106**（新增 2：双击 PATH 回退、回退候选清单）；cargo test **15/15**（新增 2：node 回退候选、first_existing）；cargo check / npm run build / tauri build 全部通过。

## 四、DMG 阶段失败分析

本机两类场景均构建成功（干净会话、挂载旧 DMG 后重建），未复现失败。`bundle_dmg.sh` 源码审查确认两个环境敏感失败点：

1. **Finder AppleScript 美化（exit 64）**：脚本用 osascript 驱动 Finder 设置窗口/图标布局。失败诱因：
   - 构建宿主终端 App 未获「自动化 > Finder」TCC 授权（首次构建弹窗被忽略/拒绝）
   - 无 GUI 会话（SSH / CI runner）
   - 已知偶发 `Can't get disk (-1728)`（脚本自带 2s sleep 规避，高负载下仍可能触发）
2. **hdiutil detach（exit 16 EBUSY）**：脚本对临时 RW 卷做挂载→美化→卸载，重试耗尽即失败。典型诱因：上一版 DMG 卷仍挂载、或旧卷内 MFP.app 仍在运行、Finder/Spotlight 占用卷。

如再次失败，取 `npm run tauri build` 输出中 `Running bundle_dmg.sh` 之后的错误行即可精确定位（64=AppleScript，16=卸载忙）。

## 五、发布产物决策

**当前 MVP 以 .app 为发布产物，DMG 非必需**：

- 单人本地工作台，无分发需求；DMG 相对 .app 不提供额外价值（未签名应用 DMG 同样触发 Gatekeeper）
- 只构建 .app：`npm run tauri build -- --bundles app`（跳过 DMG，绕开上述环境敏感阶段）
- 如后续需要 DMG 分发：在 GUI 会话终端构建、首次弹窗时同意「自动化 > Finder」、构建前推出旧 MFP 卷并退出旧 MFP.app
