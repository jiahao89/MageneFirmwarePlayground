## 一、为什么这次重构

v1.0 方案（2026-08-13）定了"软链化 + 复用成熟 skill"，但**实际落地偏离了方案**：

| v1.0 方案 | 实际落地 | 后果 |
|---|---|---|
| `knowledge-base/` 软链 workspace | 实体复制 | workspace 已新增 `码表常用组件库.md` 等，MFP 副本**正在变旧** |
| `skills/` 软链 workspace | 实体复制 | 三个画图 skill 漂移风险同左 |
| 复用 10+ 成熟 skill | 只落地 3 个画图 skill + 1 个 firmware-review | 全局成熟的 `prd-writer`/`hardware-product-analysis` 等**没接进编排** |

本次重构目标：**纠正"复制漂移"病根，把三处价值源（prd-generator 的编排范式、workspace 的知识事实、全局成熟 skill）真正焊在一起。**

## 三、目标架构（三层分离）

```

├── CLAUDE.md / AGENTS.md           ← 薄规则入口（引用其余文件，不重复内容）
├── .ai_global_profile.md           ← 软链 → workspace 同名文件（单一行为大脑）
├── .claude/
│   ├── agents/
│   │   ├── mfp-prd-flow.md         ← 主编排（本次重写：加 Phase 0.5 澄清 + 换 skill 指向）
│   │   └── mfp-reviewer.md         ← 评审编排（微调：skill 名确认）
│   └── skills/
│       └── firmware-review/        ← 唯一本地 skill（保留，按 mattpocock 范式强化）
├── skills/                         ← 全部软链 → workspace/.agents/skills/*
│   ├── magene-design → …
│   ├── figma-lofi-prototype → …
│   └── drawio-skill → …
├── knowledge-base/                 ← 软链 workspace 原始目录（不再自建重组结构）
├── config/product-line/码表/       ← 迈金写作风格 + 产品线知识包（实体，MFP 自维护）
│   ├── manifest.json / style.md
│   ├── personas.md / competitors.md   ← 从 prd-generator 迁入（如 workspace 无 1:1 对应）
│   └── samples/                        ← 成熟 PRD 样本（从 prd-generator prd-mature 迁入）
├── scripts/relink.sh               ← 软链重建兜底脚本
├── output/                         ← 需求工作包产出区（每需求一目录）
├── docs/ design/                   ← 定稿文档 / 方案文档
└── app/ worker/ db/ …              ← 冻结留档，不投入
```

**核心原则**：
1. **编排层只做编排**，不烤领域知识（agent 文件薄，指向 skill + config + 模板）。
2. **skill 层全部引用成熟件**，MFP 本地只保留 1 个固件专属的 `firmware-review`。
3. **知识/事实层软链 workspace（SSOT 只读）**，MFP 不持有第二份。
4. **迈金专属风格下沉到 config**，通用 skill 无侵入读取。

## 四、Skill 选型与映射（本次重构的核心）

### 4.1 mattpocock/skills 适用性评估（诚实校准）

mattpocock/skills 的定位是 **"Skills for Real Engineers"——给 coding agent 的可复用工程习惯**，主体是 `implement`/`tdd`/`code-review`/`diagnosing-bugs`/`resolving-merge-conflicts`/`improve-codebase-architecture` 这类**写代码**的 skill，对 MFP 的 PRD 工作流**大部分不适用**。

它对 MFP 的价值在三点，分开对待：

| 价值 | 说明 | 落地方式 |
|------|------|---------|
| ① 少数 skill 可跨界 | `grill-me`/`grilling`/`wait-what`（需求澄清）、`to-spec`（规格化）、`research`（有据调研）、`domain-modeling`（对象/词汇建模）、`handoff`（Phase 交接）、`writing-for-agents`（写 agent 可读文档） | 直接引用（已全局安装，零成本） |
| ② skill 工程化范式 | frontmatter 规范、分阶段流程、自检清单、可复用 interview pattern | 重写 `firmware-review` 时借鉴 |
| ③ 其余 80% 不适用 | 写代码/调 bug/拆 ticket 类 | 不引入，避免触发词噪音 |

> **注意**：不要因为"成熟"就全量套用 mattpocock。skill 越多，触发词互相干扰越重（v1.0 风险 2 已预警）。只引上述 7 个跨界项。

### 4.2 完整 Skill 映射表

| Phase | 任务 | 采用 skill | 来源 | 替代了 prd-generator 的 |
|-------|------|-----------|------|----------------------|
| 0.5 | 需求澄清（新增） | `grill-me` / `wait-what` | 全局（mattpocock） | —（prd-generator 无此环节） |
| 1 | 人群归位 | 无 skill，读 `6层人群模型` 模板 | workspace 知识 | — |
| 2 | 竞品调研 | `hardware-product-analysis` + `research` | 全局（官方 + mattpocock） | `web-research` |
| 3 | 需求分析 | `prd-writer`（概念版模式） | 全局（官方，多文件成熟版） | `requirements-analysis` |
| 3 | 对象/状态建模（复杂需求） | `domain-modeling` 思想 + `对象与字段清单模板` | 全局 + workspace 模板 | — |
| 4 | PRD 撰写 | `prd-writer`（落地版模式）+ `config/style.md` + 样本 | 全局 + MFP config | `prd-writer`（prd-generator 版） |
| 5 | 双视角评审 | `firmware-review` ★本地 | MFP `.claude/skills/` | `dev-review` + `qa-review` |
| 5 | 评审报告 HTML | `mfp-reviewer` 内置模板 | MFP agent | `pre-review-html` |
| 6 | 原型输入 | `magene-design` → `figma-lofi-prototype` / `drawio-skill` | workspace 软链 | —（MFP 增量） |
| 7 | 交付归档 | `docx` / `pptx` / `lark-doc` | 全局（官方） | — |

**结论：MFP 本地仅维护 1 个 skill（`firmware-review`），其余全部引用全局成熟 skill + workspace 软链 + config。**

### 4.3 关键：`prd-writer` 同名冲突的裁决

`prd-writer` 存在 3 处，本次统一裁决：

| 位置 | 裁决 |
|------|------|
| prd-generator 项目版 | ❌ 丢弃（但其**迈金专属内容**抽到 `config/style.md` + 样本） |
| `~/.claude/skills/prd-writer`（官方，多文件） | ✅ 采用（概念版→落地版两版交付） |
| `~/.agents/skills/prd-writer`（Codex） | 不引入 MFP 编排，仅 Codex 侧自用 |

**原理**：官方 `prd-writer` 是"通用 PRD 方法论"，不知道迈金 PRD 长什么样；迈金专属风格（嵌套结构 / Toast 精确到字 / 国内海外标注 / 弹窗优先级 / @人名）由 `config/style.md` + `prd-mature` 样本注入，两者解耦。
