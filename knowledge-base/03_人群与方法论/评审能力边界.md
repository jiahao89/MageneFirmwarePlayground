# 评审 Skill 的能力边界（能评什么、不能评什么）

> 来源：提炼自迈金 PM 工作区 `05_AI协作评测/origin.md`（《讲透需求评审 Skill(6)》）。
> 用途：决定何时让 firmware-review 先跑、何时人先主导；避免对 AI 评审抱错误预期。

## 一、Skill 擅长的：「有没有」和「对不对」

| 类型 | 说明 | 对应 firmware-review 检查 |
|------|------|--------------------------|
| ① 完整性缺失 | 验收标准没写、异常流程缺失、三层架构不完整 | mode=qa 状态机覆盖 / mode=dev 三层架构 |
| ② 逻辑矛盾 | 同一功能两处描述不一致、状态流转有死路、正文与待确认项打架 | SSOT 一致性 / 交叉比对 |
| ③ 同类经验匹配 | 把当前需求与历史 benchmark 对照，找出上次踩过的坑 | Phase 0 事实源召回后逐条比对 |

## 二、Skill 不擅长的：「好不好」和「该不该」

| 类型 | 为什么评不到位 | 交给谁 |
|------|---------------|--------|
| 强业务判断 | "该不该做/优先级对不对"答案在业务里，不在文档里 | PM |
| 团队潜规则 | "这个接口动不得/历史债重"不成文 | 资深研发/PM |
| 创新/探索型 | 没有基准，给的只是泛泛意见 | PM + 研发共创 |
| 跨系统联动 | 需要同时懂 A/B/C 系统，知识库难覆盖且易过时 | 各系统 owner |
| 用户体验/产品方向 | 交互好不好靠用户洞察，不是规则匹配 | PM / 设计 |

## 三、中间地带：加了知识能评，但有成本

- 复杂业务背景：把调度/算法/运力模型写进知识库后能评，但建设+维护成本高，只在高频高价值领域划算。
- 合规标准（支付/隐私/安全）：有明确外部标准，写入知识库后覆盖好，成本低、值得做。
- 公司内部规范（接口/命名/交互）：能做一致性检查，但规范本身常不成文，整理比写 skill 更费劲。

## 四、最有效的分工方式

1. **firmware-review 先跑**：把完整性、逻辑矛盾、可测试性、与 benchmark 的冲突全部扫出来。
2. **人聚焦 skill 发现不了的**：业务判断、潜规则、系统联动、产品方向。
3. 两者分工，不是二选一——AI 评审不是来替代你，是替你做"你做了也不会更好"的重复检查，把"只有你能做"的判断留给你。

## 五、实操规则（写入评审工作流）

- 常规功能迭代 / 文档质量参差 / 新人评审 / 时间紧 → 让 firmware-review 先跑。
- 探索型 / 强业务判断 / 跨系统深度联动 / UX 方向 → 人先主导，skill 作补充。
- 评审报告结尾固定一句："本报告为 AI 产出，所有 🔴 结论请研发/QA 复核后关闭"。
